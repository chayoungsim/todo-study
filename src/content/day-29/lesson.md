## 좋은 설계란?

설계에는 정답이 없습니다. 기준은 하나입니다. **나중에 바꾸기 쉬운가?**
요구사항은 반드시 바뀌고, 그때 고칠 곳이 **한 군데**이면 좋은 설계입니다.

## 컴포넌트를 나눠야 한다는 신호

처음부터 잘게 나눌 필요는 없습니다. 다음 신호가 보일 때 나눕니다.

- 파일이 **너무 길어져** 한눈에 안 들어온다 (대략 200~300줄 이상)
- 컴포넌트 이름을 짓기 어렵거나, 설명에 **"그리고"** 가 들어간다
- state와 props가 **너무 많아** 어디서 바뀌는지 따라가기 힘들다
- 같은 JSX 덩어리가 **여러 곳에서 반복**된다
- 일부만 바뀌는데 **전체가 다시 렌더링**된다 (Day 11)

## 책임에 따라 나누기

한 컴포넌트가 계산, 상태 관리, 화면 그리기를 모두 하면 이해하기도, 테스트하기도 어렵습니다. 네 층으로 나눠 보세요.

| 층 | 하는 일 | 형태 | 테스트 |
|---|---|---|---|
| **계산** | 합계, 할인, 해금 규칙 같은 순수한 규칙 | 평범한 함수 | 매우 쉬움 |
| **로직** | 상태와 변경 방법 | 커스텀 훅, reducer, 스토어 | 보통 |
| **화면 조각** | 받은 props로 UI를 그림 | 컴포넌트 | 시각 확인 |
| **조립** | 위 셋을 엮어 한 화면을 만듦 | 페이지 컴포넌트 | 흐름 확인 |

이 사이트도 이렇게 나뉘어 있습니다.

- `src/lib/progress.ts`: 해금, streak, 채점 **순수 함수** (단위 테스트 대상)
- `src/stores/progressStore.ts`: 진행 상태를 담은 **로직**
- `src/components/day/*`: 화면 조각 (`Quiz`, `Markdown`, `CodeSandbox`)
- `src/pages/*`: 조립

날짜 경계처럼 버그가 나기 쉬운 규칙을 **순수 함수로 뽑았기 때문에** 컴포넌트 없이 시간대까지 바꿔 가며 테스트할 수 있었습니다.

## 순수 함수를 먼저 떠올리기

```tsx

function Cart({ items }) {
  const total = items.reduce((sum, i) => sum + i.price * i.qty, 0);

// 순수 함수로 뽑으면: 입력 → 출력만 확인하면 된다

expect(calcTotal([{ price: 60000, qty: 1 }]).discount).toBe(6000);
```

## 상태는 어디에 둘까? (결정 순서)

위에서부터 차례로 따져 보고, **가장 가까운 곳**에 둡니다.

1. 한 컴포넌트만 쓴다 → `useState`
2. 형제나 가까운 몇 개가 쓴다 → 공통 부모로 **끌어올리기** (Day 7)
3. 상태 변경 규칙이 복잡하다 → `useReducer` (Day 8)
4. 멀리 있는 여러 곳이 쓰는 **UI/앱 상태** → Context 또는 Zustand (Day 7, 21)
5. **서버에서 온 데이터** → TanStack Query (Day 27)
6. 새로고침해도 필요한 **화면 보기 방식**(필터, 정렬, 페이지) → 주소의 검색 파라미터 (Day 25)

"일단 전역 스토어에 넣자"가 가장 흔한 실수입니다. 필요가 생길 때 **한 단계씩 올리세요.**

## 폴더 구조

정답은 없지만 원칙은 있습니다.

- **함께 바뀌는 것은 가까이** 둡니다. (한 기능의 컴포넌트, 훅, 타입을 한 폴더에)
- **의존 방향을 한쪽으로**: 페이지 → 컴포넌트 → 훅/라이브러리 순서로만 가져다 씁니다. 거꾸로 가져오면 순환이 생깁니다.
- **너무 깊이 중첩하지 않습니다.** 찾기 어렵습니다.

이 프로젝트의 구조입니다.

```
src/
├─ app/          앱 진입점, 라우팅
├─ pages/        화면 하나당 폴더 (조립)
├─ components/
│  ├─ ui/        shadcn 기본 부품 (버튼, 대화상자)
│  ├─ layout/    사이드바, 헤더
│  └─ day/       학습 화면 전용 조각
├─ config/       브랜드 이름 같은 상수
├─ hooks/        여러 곳에서 쓰는 훅
├─ stores/       Zustand 스토어
├─ lib/          React 와 무관한 순수 로직과 테스트
└─ content/      학습 콘텐츠 (day-NN 폴더)
```

규모가 커지면 `pages/` 안에 그 화면에서만 쓰는 컴포넌트를 함께 두거나, **기능별 폴더**(`features/cart/…`)로 바꾸기도 합니다. 지금 구조가 불편해질 때 바꾸면 됩니다.

## 너무 이른 추상화를 조심하기

중복을 싫어한 나머지 **한 번 쓰는 코드까지** 공통 컴포넌트, 공통 훅으로 만들면 오히려 고치기 어려워집니다.
"**세 번 반복되면 추출한다**"(Rule of Three)를 기준으로 삼으세요. 두 번까지는 복사해도 괜찮습니다. 모양이 확실해진 뒤에 합쳐야 잘못 합치지 않습니다.

## 이름 짓기

- 이벤트 핸들러: 만드는 쪽은 `handleSubmit`, props로 받는 쪽은 `onSubmit`
- 불리언: `isOpen`, `hasError`처럼 질문 형태로
- 훅은 `use`로 시작, 컴포넌트는 대문자 시작
- 이름을 짓기 어렵다면 책임이 둘 이상이라는 신호일 수 있습니다.

## 오늘의 정리

- 좋은 설계는 나중에 바꾸기 쉽다. 신호가 보일 때 나누고, 미리 잘게 나누지 않는다.
- 계산(순수 함수), 로직(훅), 화면 조각, 조립으로 책임을 나누면 테스트하기 쉽다.
- 상태는 가장 가까운 곳에 두고, 필요할 때 한 단계씩 올린다.
- 함께 바뀌는 것은 가까이, 의존 방향은 한쪽으로. 세 번 반복되면 추출한다.
